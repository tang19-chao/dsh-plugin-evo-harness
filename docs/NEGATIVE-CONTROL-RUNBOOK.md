# 负控制操作规程（Negative-Control Runbook）

> 来源：2026-10-29 的 P2–P6 执行轮。本文把那几轮学到的纪律**写成可执行的形式**，因为
> 那一轮反复出现同一个失效形状——**一条检查比它声称的范围窄，却以合格的形式输出**。
>
> 本文不是原则清单：每条规则都给出可直接粘贴的命令。**但不是每条都以布尔值结束**——
> 规则 4 输出 True/False（它有可判定的性质），规则 3 以退出码 2 表示变异无效，
> 规则 1/2/5 是命令或写作要求。**别让头部的承诺超过实际做到的**——那正是本文批评的形状。

## 0. 为什么需要这份文件

那一轮发生过下面四件事，每件都是同一个形状：

| # | 事件 | 声称 | 实际检查了什么 |
| --- | --- | --- | --- |
| 1 | 变异删除守卫后还原，报 `BYTE-IDENTICAL: True` | 「我没有损坏文件」 | 「我备份的那份 == 我还原回的那份」（之后文件又被编辑，最终交付物已漂移；备份已被删，无法复核） |
| 2 | 给某条观测差异贴上「时点漂移」 | 「文件过期了」 | 没有核对 mtime；实际是自己读错 |
| 3 | 报 `mutation-gate` 红为「CRLF 瞬态」 | 「CRLF 会让门禁随机红」 | 门禁脚本本身 EOL 自适应；命题不成立 |
| 4 | 本文规则 4 的第一版：把 `$hFinal` 写在 `$h2` 下一行 | 「交付物未变」 | `$h2` 与 `$hFinal` 之间零文件操作 ⇒ 等式**恒真**。三次不同内容、一次真实后续编辑，它也照样打印 True |

**共同点**：证据的**形式**（True）比它的**范围**权威得多。

第 4 条尤其要记住：它**比前三者更糟**，因为前三者至少在条件不利时会输出 False，而恒真的检查
永远输出 True。**一条恒真的检查无法报警。** 本文每条规则的「失效形状」都应据此自检：
它有没有可能在**任何**情况下都为真？

## 1. 规则 1（前置检查）：动手前看清会波及什么

```powershell
git status --porcelain -- <target>
```

破坏性操作的范围**不由你正在编辑什么决定，而由文件里还藏着什么决定**。本仓按惯例整轮不 commit，
所以每一次 `git checkout -- <file>` / `git restore` / `git stash` 都是一次**不可恢复的删除**。
在一个未提交的工作树上，禁止用这三条命令「还原」。

## 2. 规则 2（副本）：变异只发生在副本上 —— 且三个产物必须按目标隔离

**先定义三个按目标隔离的产物路径，后面所有规则只引用这三个变量，不再出现任何字面路径。**

```powershell
# slug 必须来自完整路径，不能是 basename：pkgA/gate.mjs 与 pkgB/gate.mjs 的 -Leaf 都是 gate.mjs，
# 三个产物会重新碰撞，数据损坏原样回归。取相对路径的哈希前 12 位。
$rel = [IO.Path]::GetRelativePath((Get-Location).Path, (Resolve-Path <target>).Path)
$slug  = [BitConverter]::ToString([Security.Cryptography.SHA256]::Create()
           .ComputeHash([Text.Encoding]::UTF8.GetBytes($rel))).Replace('-','').ToLower().Substring(0,12)
$bak    = "work/neg-control.$slug.keep-bak"
$red    = "work/neg-control.$slug.red.log"
$anchor = "work/neg-control.$slug.h1"

# 每一次变异的身份：snippet 的哈希。三个产物共用同一个身份键，守卫必须读全。
$snippetHash = [BitConverter]::ToString([Security.Cryptography.SHA256]::Create()
           .ComputeHash([Text.Encoding]::UTF8.GetBytes('<guarded snippet>'))).Replace('-','').ToLower()

Copy-Item <target> $bak
```

### 身份键完整性：本文所有守卫的统一判据

每一份跨越进程边界的记忆都有**身份键**；守卫必须比对身份键的**全部维度**。
少比对一维，上一次实验的记忆就会被当成这一次的。

| 产物 | 身份键 | 必须比对 | 少读一维的后果 |
| --- | --- | --- | --- |
| `$bak` | relpath | 路径唯一性（由 slug 保证） | 数据损坏 |
| `$anchor` | relpath + h1 | target 与 h1 两项 | 假警报 / 假通过 |
| `$red` | relpath + **snippetHash** | target 与 snippet 两项 | **同一目标两次不同变异互相认证** |

### 统一自查判据：反例构造法

**不要问「守卫读了几维」，问：「我能构造出一个让它返回 False 的输入吗？」**

```text
对每个守卫，写一行"期望它失败"的输入，然后真的跑一次：
  构造不出来          -> 守卫是空的（恒真 / 比占位符 / 空值匹配任意）  ← 最危险
  能构造，但那是"上一次实验" -> 防不住陈旧记忆                      ← 少读一维
  能构造，但真实运行中不可能出现 -> 防的是不存在的风险
```

**为什么它比「读了几维」更强**：「读了几维」只能发现**维度缺失**；
若守卫比的是一个**不存在的维度**（例如写成字面量 `'<target>'` 而不是 `$target`），
维度计数看起来完全正常，而守卫恒真。**只有『反例能否构造』同时覆盖两者。**

**反例构造法在本文件抓到的实例**（每一条都不要重复犯）：

| # | 守卫 | 反例 | 教训 |
| --- | --- | --- | --- |
| 1 | 只有 `h1 -eq h2` | 还原后又编辑 | 证明的是 restore，不是 deliverable |
| 2 | `$hFinal` 写在同一段脚本 | —— | 恒真；时间间隔必须跨进程 |
| 3 | 无规则要求「红」 | 跳过 3.5 走完全程 | 缺一整条规则 |
| 4 | 三产物只隔离 anchor | 两目标交错 | 修实例不修类 |
| 5 | `$red` 只比 target | 同 target 另一次变异 | 少读一维 |
| 6 | 比字面量 `'<target>'` | **构造不出来** | 读了不存在的维度 —— 恒真 |
| 7 | 4b 用内存里的 `$snippetHash` | fresh 进程里为 `$null` | **空值拼进字符串静默变空串，匹配任意** |

**为什么三个都要隔离，而不是只隔离 anchor。** 固定路径在「一个任务里有两个目标、且交错执行」时会有两种后果，
实测均成立：

| 产物 | 固定路径的后果 | 严重度 |
| --- | --- | --- |
| `keep-bak` | 对 X 做完规则 2 后、尚未做 4a 时对 Y 做规则 2 → 备份被 Y 覆盖 → 回头完成 X 的「还原」时 **X 的内容变成 Y 的内容** | **数据损坏** |
| `red.log` | 对 A 的负控制写出红日志后，对 B 做一次**存活**变异（不写红日志）→ B 的 4b 读到 A 的日志 → `evidence-valid: True` | **假通过** |
| `anchor` | 对 A 做 4a 后对 B 做 4a → 回查 A 报 `False` | 假警报 |

**这不是并发竞态——串行操作就会触发**，只要一个任务里有第二个目标。
**注意第一种**：这条规则的设计目的是「保证不损坏文件」，而它自己可以损坏文件——**修一个实例（anchor）不等于修一个类（固定路径 + 多目标）**。

## 3. 规则 3（变异必须真的生效）：先证明变异应用了，再看测试红不红

```powershell
$before = Get-Content $bak -Raw    # $bak 来自规则 2 的按目标隔离定义
$mut = $before.Replace('<guarded snippet>', '<broken variant>')

# 检查 1（最弱）：内容变了没有。这只能证明"文件被写过"。
if ($mut -eq $before) { Write-Output 'MUTATION-DID-NOT-APPLY'; exit 2 }

# 检查 2（真正的判据）：目标串必须真的消失。
# 检查 1 通过而检查 2 失败，说明变异命中了一段"看起来像但并不是"的文本——
# 这次变异没有触及守卫，负控制是假的。
if ($mut.Contains('<guarded snippet>')) {
  Write-Output 'MUTATION-LEFT-GUARD-INTACT'
  exit 2
}
Write-Output 'guard-removed: True'
Set-Content -Path <target> -Value $mut -NoNewline
```

**两个检查都要有，且检查 2 才是判据。** 只用检查 1 会放行一次没有触及守卫的变异——实测反例：
文件里同时有 `if (guarded === true)`（真守卫）与 `guarded flag`（注释里的相似词）时，
只替换后者，`$mut -ne $before` 成立（检查 1 通过），而真守卫完好无损。

**这个坑在三种情况下必然出现**：变异目标是正则、片段在文件中有多个近似写法、或用了 `-replace`
（正则）而不是 `.Replace`（字面）。规则 3 存在的全部理由就是防这种情况。

判据是「目标串在新内容里已消失」，**不是**「测试红了」。测试没红有两种完全相反的含义：
变异没生效，或守卫没有被覆盖。

## 3.5 规则 3.5（把「红」落成证据）：变异必须真的被测试抓到

**规则 3 证明变异被应用了，规则 4 证明文件被完整还原了——但这两条加起来仍不证明「这个变异被测试抓到过」。**
一个只跑规则 1/2/4、跳过规则 3 与 3.5 的人，会拿到两条 `True`，而**那一轮什么都没发生**。
第三段恰恰是负控制的全部意义。

```powershell
$out = & <test-command> 2>&1 | Out-String
$code = $LASTEXITCODE

# 顺序至关重要：先判断，后写日志。
# 如果先写日志再判断，变异【存活】(exit 0) 时也会留下一条带着完整合法标记的红日志，
# 而 4b 只读文件、读不到退出码 —— 存活变异会被认证成"被杀死的变异"。
if ($code -eq 0) {
  Write-Output 'mutant-went-red: False'
  Write-Output 'MUTANT-SURVIVED'
  exit 3
}
Write-Output 'mutant-went-red: True'

# 只有真正红了才写日志，且必须写全身份键（relpath + snippet），供 4b 逐项比对。
$stamp = 'target=' + <target> + ';snippet-sha256=' + $snippetHash
$stamp | Set-Content $red -Encoding utf8
$out | Add-Content $red -Encoding utf8
```

**这条顺序不是风格问题。** 退出码是「只存在于那次进程里的记忆」——4b 在另一次调用中读不到它，
能读到的只有磁盘上的日志。所以**日志只能由成功路径写入**，否则它证明不了任何事。

**红必须离开屏幕。** 一个只在终端里出现过的红，在事后无法区分于「我从没跑过」。
日志文件是那段实验唯一的外部痕迹。

**但「有日志」不够，还要「对上号」。** `Test-Path $red` 只问有没有一个红日志，不问是不是**这一次**的红：
对 A 的负控制写出日志后，对 B 做一次**存活**变异（不写日志），B 的 4b 会读到 A 的日志并输出 `True`——
**一个存活变异被认证成被杀死的变异**。所以日志首行必须带 `target=` 与 `snippet-sha256=`；
4b 不仅要求文件存在，还要求这两个值与本次一致。

**规则 4b 的完成条件因此多一项**：`evidence-valid` 需要「哈希相等」**且**「本文档 3.5 的日志存在且标记匹配」。
哈希相等但没跑过测试、或跑的是另一个目标的测试，都等于**一次没做的实验出具了合格的收尾证据**。

## 4. 规则 4（三处同刻取样）：还原 + 交付物都必须是同一个哈希

**必须分成两次独立调用。** 一段连续脚本**做不到**这件事——原因见下方「为什么必须是两次调用」。

阶段 A —— 做负控制时执行：

```powershell
# $bak / $red / $anchor / $slug 来自规则 2 的按目标隔离定义，此处不再写字面路径
$h1 = (Get-FileHash $bak -Algorithm SHA256).Hash.ToLower()
Copy-Item $bak <target> -Force
$h2 = (Get-FileHash <target> -Algorithm SHA256).Hash.ToLower()
Write-Output ('restore-identical: ' + ($h1 -eq $h2))

# 锚点同样按目标隔离：固定文件名会让"对 A 做 4a、对 B 做 4a、再回来查 A"互相覆盖，
# 于是 A 从未变过却报 False —— 假警报会让人开始不信这条规则，然后连真的警报也不信。
# 锚点同时承载 snippetHash：4b 在另一次调用里执行，PowerShell 变量不跨进程，
# 若 4b 依赖内存里的 $snippetHash，它在 fresh 进程里是 $null —— 而 $null 拼进
# 字符串会静默变成空串，使 "*snippet-sha256=*" 匹配任意日志。所以身份键必须落盘。
Set-Content $anchor @"
target=$target
h1=$h1
snippet-sha256=$snippetHash
"@ -Encoding ascii
```

阶段 B —— **另一次调用**，在所有合法编辑做完之后执行：

```powershell
# $bak / $red / $anchor / $slug 来自规则 2 的按目标隔离定义
$anchorText = Get-Content $anchor -Raw
$anchorTarget  = (($anchorText -split "`n") | Where-Object { $_ -like 'target=*' })          -replace '^target=', ''
$h1            = (((($anchorText -split "`n") | Where-Object { $_ -like 'h1=*' })            -replace '^h1=', '')).Trim()
# snippetHash 从锚点读，不从内存变量读：4b 在另一次调用里执行，变量不跨进程。
$snippetFromAnchor = (((($anchorText -split "`n") | Where-Object { $_ -like 'snippet-sha256=*' }) -replace '^snippet-sha256=', '')).Trim()

# 锚点必须属于同一个目标；否则读数无意义（见规则 2 的隔离说明）
if ($anchorTarget -ne $target) { Write-Output 'ANCHOR-TARGET-MISMATCH'; exit 4 }
# 身份键不得为空：空值会让下面的 -like 退化成"匹配任意"。
if ([string]::IsNullOrWhiteSpace($snippetFromAnchor)) { Write-Output 'ANCHOR-SNIPPET-MISSING'; exit 5 }

# 红日志不仅要存在，还要"对上号"：首行必须记录本次的 target
$redLogged = Test-Path $red
$redLine = if ($redLogged) { (Get-Content $red -TotalCount 1) } else { '' }
# 身份键有两维，必须两维都比：只比 target 的话，同一目标的两次不同变异会互相认证。
# 两维都来自锚点（磁盘），不来自内存变量——见 4a 的说明。
$redTargetOk  = $redLine -like ("*target=" + $target + ";*")
$redSnippetOk = [bool]$snippetFromAnchor -and ($redLine -like ("*snippet-sha256=" + $snippetFromAnchor + "*"))
$redMatches   = $redLogged -and $redTargetOk -and $redSnippetOk

$hReal = (Get-FileHash <target> -Algorithm SHA256).Hash.ToLower()
Write-Output ('hash-unchanged-since-restore: ' + ($h1 -eq $hReal))
Write-Output ('red-was-recorded: ' + $redLogged)
Write-Output ('red-target-matches: '  + $redTargetOk)
Write-Output ('red-snippet-matches: ' + $redSnippetOk)
Write-Output ('evidence-valid: ' + ($h1 -eq $hReal -and $redMatches))
```

**为什么必须是两次调用**：要证明的性质是「**在这段等待期间文件没有变**」。任何把等待写在同一段脚本里的
写法，都无法证明「等待期间」真的存在过——它只是连续执行，两次 `Get-FileHash` 之间零毫秒，等式按构造恒真。
**能被证明的时间间隔，必须跨越一个进程边界**（磁盘文件 / 独立调用）。这是本规则唯一能真实成立的形式。

**本规则自己的失效形状：恒真。** 如果 4a 与 4b 被粘贴进同一次执行，`$h1 -eq $hReal` 会因为「中间什么都没发生」
而无条件为 True——**一条恒真的检查无法报警，比一条范围过窄的检查更危险，因为它看起来永远合格。**

**大小写**：`Get-FileHash` 返回大写，`node crypto` / `sha256sum` / `git hash-object` 返回小写。
一律 `.ToLower()`，并在报告里声明比较口径；否则第三方用另一种工具逐字比较会出现**假不匹配**。

## 5. 规则 5（写进报告时）：一条自述证据必须能被第三方复现

报告中的哈希必须附**完整命令 + 取样时刻**，且第三方在最终树上重跑同一条命令能得到同值。
做不到这一点，就不是证据，是叙述。

## 5.5 汇总断言：部分通过不能看起来像全部通过

逐条输出（`restore-identical` / `red-was-recorded` / `evidence-valid`）在屏幕上排列整齐，
但**「三条里过了两条」与「三条全过」在观感上没有区别**。收尾必须有一条汇总：

```powershell
# $bak / $red / $anchor / $slug 来自规则 2 的按目标隔离定义
$anchorText = Get-Content $anchor -Raw
$h1 = (((($anchorText -split "`n") | Where-Object { $_ -like 'h1=*' }) -replace '^h1=', '')).Trim()
$hNow = (Get-FileHash <target> -Algorithm SHA256).Hash.ToLower()

# 身份键两维都要比（relpath 由 slug 保证、snippet 必须逐字比），不能只比 target。
$redLine = if (Test-Path $red) { (Get-Content $red -TotalCount 1) } else { '' }
$anchorText2 = Get-Content $anchor -Raw
$snip = (((($anchorText2 -split "`n") | Where-Object { $_ -like 'snippet-sha256=*' }) -replace '^snippet-sha256=', '')).Trim()
$redOk = ($redLine -like ("*target=" + $target + ";*")) -and
         [bool]$snip -and
         ($redLine -like ("*snippet-sha256=" + $snip + "*"))

Write-Output ('NEGATIVE-CONTROL-COMPLETE: ' + ($redOk -and ($h1 -eq $hNow)))
```

把这一行贴进报告。**报告里只引用这一行**，不要引用中间过程——中间过程是给人看的，
汇总行是给下一个复核者用的：它要么是 True，要么不是。

## 6. 适用范围

- 适用于任何「先破坏、再验证、然后还原」的验证手法：变异测试、负控制、临时补丁、故障注入。
- 不适用于对已提交文件的常规编辑——那里 `git diff` 本身就是复核途径。

## 7. 反例构造法的解读规则（不是「已知边界」，是必须遵守的读法）

判据本身是**重言式**，所以它不能被反驳——这一点要先说清楚，否则下面四条会被误读成「判据有时会失灵」。

**为什么它不能被反驳**：空守卫的定义就是「不排除任何东西」；判据「构造不出反例 ⇒ 空」改写后是
「不存在反例 ⇒ 不存在反例」。反证：若某个守卫排除了 X，则 X 中的输入就是反例，
故「排除」蕴含「有反例」，其逆否即「无反例」蕴含「空」。**它在逻辑上不可能有反例。**

**它的价值是转换，不是断言**：

| 问法 | 需要什么 | 可执行吗 |
| --- | --- | --- |
| 「这个守卫完备吗？」 | 必须先知道全部身份维度 | 常常**不可知**——你不知道自己漏了什么 |
| 「我能让它失败吗？」 | 只需要**尝试** | **总是可以尝试** |

它把一个需要先验知识的问题，换成一个只需要努力就能推进的问题。**它不是陈述事实，是重写工作流程。**

### 因此，「构造不出」有四种读法，必须区分

```text
构造出反例，且它属于真实威胁      -> 守卫有洞，修
构造出反例，但它不可能真实发生    -> 守卫防的是不存在的风险，可删（减少噪音）
构造不出，且变异空间已穷举        -> 守卫是空的，危险
构造不出，但变异空间未穷举        -> 【未知】不是「安全」，是「还没查到」
```

**第四行是本节存在的唯一理由。** 把「构造不出」从「通过」里摘出来、单列成「未知」——
否则下一个用这份文件的人会把「我没找到反例」读成「没有反例」，而那正是本文从 §0 起就在防的形状。

### 变异空间不止一个（实测）

「构造不出」几乎总是「在错误的变异空间里找」。同一个守卫，换空间反例就出现了：

| 守卫 | 直觉上的空间 | 反例真正所在的空间 |
| --- | --- | --- |
| 「等待期间文件未变」（`Start-Sleep` 前后取哈希） | 运行时数据 | **并发现象**——等待期间另一个进程写文件，哈希立刻不等 |
| TypeScript `const _exhaustive: never = x` | 运行时数据（看起来任何输入都不会失败） | **输入域（源码）**——给联合类型加一个成员，`tsc` 立刻报 `TS2322` |
| 「红日志的 snippet 匹配」 | 运行时数据 | **进程边界**——4b 在另一次调用里，内存变量为 `$null` |

**一个只在『运行时数据』里造反例的测试者，会把前两者都误判为「空」——而它们都不是。**
所以准确的表述是：

> 判据本身可靠；但「构造不出」永远只能读作「**在当次想象的变异空间里**构造不出」。
> **它不是守卫的属性，是测试者与守卫之间关系的属性。**

### 操作层要求：清单必须**可核查**，不能只是"存在"

**「写明尝试了哪些变异空间」这一条，本身有三个强度层级——只有一个能真的挡住错误：**

| 层级 | 检查什么 | 可机械化 | 能否抓住「清单只有一项」 |
| --- | --- | --- | --- |
| ① | 空间清单**存在** | ✅ 正则 | ❌ 不能 |
| ② | 至少列出 **2** 个空间，且每个说明怎么试 | ✅ 计数 | ✅ **能** |
| ③ | 每个空间都留**落盘痕迹**（`work/space-<name>.log`） | ✅ 文件存在性 | ✅ 能，且最强 |

**只做第 ① 层等于没做。** 一份「完全合规但结论错误」的报告长这样：

```text
guard      : 等待期间文件未变（sleep 前后取哈希）
result     : 构造不出反例
变异空间   : [运行时数据]（已穷举）      ← 清单在场、格式合规
conclusion : 守卫是空的
```

它满足第 ① 层，而结论是错的（反例在**并发**空间）。**读者无法从报告本身察觉**——
清单在场，只是不完整。**这就是"存在性检查"被当成"正确性检查"的现场。**

### 一个填好的空间清单（照抄这个格式）

```markdown
guard: 等待期间文件未变（hash before/after sleep）
结论: 构造出反例

尝试的空间（至少两项，每项附实测痕迹）:
  - 运行时数据: 直接改文件内容 → hash 变化 → 反例成立（实测 content=v2-MODIFIED）
  - 并发:       等待期间另一进程写入 → hash 变化 → 反例成立
  - 进程边界:   不适用（该守卫不跨进程）
```

**有样例的规则才会被照着做；没有样例的规则只会被引用。** 本文 §7 前半段已经说过
「判据的价值是转换」，这一节把同样的道理落到**格式**上：不给样例，下一个用者会自己发明一个
恰好能通过检查的格式。**

**报告里没有「至少两个空间 + 各自实测痕迹」，就按『未知』处理，不得写成『构造不出』（=通过）。**

## 8. 本文件保护不了什么（先读，再信任它）

本文的全部规则都可能被**合规地绕过**。这不是缺陷，是要写清楚的事实——**以为文件会保护你，比没有文件更危险。**

### 三件本文件做不到的事（均已实测）

**1. 它只能让「缺清单」看得见，不能让「清单不全」看得见。**
§7 要求空间清单至少两项，但**一份只列两项、却漏掉真正关键空间的合规报告，本文件无法识别**。
实测：一份写着 `变异空间: [运行时数据]` 的报告，格式完全合规，而结论是错的（反例在并发空间）。

**2. 它抓不住写下它之后的第一次错误。**
实证：§7 的规则在写下之后，作者本人仍然得出「等待型守卫构造不出反例」的错误结论。
**规则在场，人照样犯错。** 当时真正起作用的是**另一个人的复查**，不是这份文件。

**3. 它没有能力判断「你是不是真的试过」。**
除非按要求落盘（`work/space-*.log`），否则「我试过并发空间」是一句可写可不写的叙述。

### 因此：本文件的定位

> 它提高**一次认真复查**的成功率，但**不能替代复查**。
> **「违反能被读者立刻看出来」是错的**——准确的说法是：
> **「缺清单」能被看出来；「清单不全」只能靠对手，或靠每个空间留一次实际尝试的记录。**

### 一个反例，说明这份文件怎么被用错了

```text
某人写: "我按 runbook 走完了全部 8 节，负控制通过。"
读者读: "有规程背书，应该没问题。"
事实  : 他可能每节都只做了第 ① 层（清单存在、日志存在、布尔为 True），
        而每一项的强度都有不止一层。
```

**每一项要求都有「形式满足」与「实质满足」两层，本文件无法替你区分它们。**
唯一能区分的方式，仍然是**另一个有动机挑错的人**。

## 9. 本文件的来历（只写可核查的部分）

本文件由一人撰写并维护，**它不是一次写成的**。

**关于它被推翻过多少次、由谁推翻：本文件不作数量声明。** 原因是可核查性——
那些过程记录在团队协作状态里，而该状态**不随仓库分发**（`.gitignore` 忽略了 `.agent-teams/`）。
写下一个下一任读者无法打开账本去核对的数字，就是本文 §0 定义的那个形状：
**声称的范围比证据的范围宽。** 这条约束同样适用于本文自己的履历。

因此，判断这份文件可信到什么程度，**方法不是读这段来历，而是做一个动作**：

> 挑本文的任意一条规则，对它做一次「反例构造法」——
> **如果能构造出让它失效的输入，它就在该处有洞（修它）；
> 如果构造不出，且你能想到的变异空间都被试过，它就更可信一点；
> 如果你一次都构造不出来、也想不出该试哪些空间，那它对你而言只是一段散文。**

**本文件的可信度不是一个已经发生的事实，而是一次正在进行的检验。**
它不能用自己的履历为自己背书——这正是 §8 的立场应用到它自己身上的结果。

## 10. 第 4 条边界：它会固化错误，而被固化的对象没有声音

§8 列的三条做不到的事，全部是「**文件管不住活人**」。还有第四条，方向相反：

**文件管不住它自己写下的东西。**

文件、历史记录、已离开的人**无法提供反证**。因此「未核即归因」对它们的后果不是错一次，
而是**把一个错误变成后人会照着执行的事实**。其他所有失效都能被「再核一次」纠正
（哈希错了重算、计数错了再数），**只有这一类不能**——它没有自我修正的机会。

### 这条已在真实交付物里发生过一次（不是假想）

一份验证报告**曾经**在 **§6.3 越界扫描**与 **§7 残余风险表**里，把一处**正确**的文件路径记成
「文档路径错误」「应修正该报告一行」。事实是该文件从一开始就是对的，错的是那次读取。

更正确实写了，但在**另一个章节**（§11.6）里，**距原错误有数屏之遥**。而读者的自然路径是：
摘要 → 越界扫描 → 风险表 → **据此决定要不要去改那个文件**。
**他会在风险表停下，永远不会读到 §11.6。**

**在补上双向指针之前，那份报告就是这个状态。** 现在它已修复（§6.3 与 §7 各加同址指针、
撤销行独立成行、§11.6 有反向指针）——**所以本段记录的是「曾经的状态 + 已如何修复」，
不是它现在的状态。** 引用别人的错误时，必须同时说明它是否已被修复；
否则本文会用一句「某人犯了 X」制造一个新的、关于已修复事项的不实陈述。

**这里刻意不写具体行号——包括"准确"的行号。**

本文初稿写的是「235 行之后」——那量的是**更正段落开头**，在写作时刻是准确的；
补指针后**同一锚点**变成 **239**（+4 = 新增的 1 行撤销行与 3 行反向指针）。
**换一个锚点会得到另一个数字**：量「更正结论句」得到 243，量「反向指针」得到 236。
**所以真正的缺陷不是某个数字算错，而是「距离」这个词没有指定锚点。**

> **本文的一段修订史，本身就是这条规则的实例。** 初版写下 235（未核）；修订版改为 243
> （换了锚点却没说明）；该修订被复核者判定为"数字错误"，本文据此写下"243 已被推翻"——
> **而那句话才是错的**（243 是真实距离，只是锚点不同）。复核者随后主动纠正了自己的误判。
> 于是本段最终形态是：**不写任何数字，只写「锚点必须指明」与「现算的定位命令」。**
>
> 教训有两条，方向相反：
> 1. **写数字前要核**（作者三次未核：235、243、以及把"命令能跑"当成不需要实测）。
> 2. **指控别人的数字错之前，要先确认那是错，而不是你的锚点不同**（复核者的一次误判，
>    因为它被采信，一度被制度化进本文件）。

一条在写作时刻为真的数字，写进一份长期存在的文件后就会过期；
**行号不是证据，因为它既会漂移，也依赖锚点的选择——本段自己也在其中。**
需要精确距离时，现算，不要引用：

```powershell
$all = Get-Content <report>
# 每个匹配串都必须落在唯一一行上；靠 _First 1_ 兜底是运气，不是正确性。
($all | Select-String '^\| \*\*T-3\*\*' | Where-Object { $_.Line -like '*文档路径错误*' } | Select-Object -First 1).LineNumber  # 原错误
($all | Select-String '反向指针（与'                                                     | Select-Object -First 1).LineNumber  # 反向指针
($all | Select-String '^t12 报告 §6.3 的'                                                 | Select-Object -First 1).LineNumber  # 更正正文开头
```

**"命令必须实际跑出东西"——这几条命令在写入本文前已在交付树上实测。**

**并且每条匹配串都必须唯一命中。** 本文前一版的命令 (a) 模式 `^\| \*\*T-3\*\*` 在报告里有
**两处**命中：错误行本身，以及它自己的更正记录行。靠 `Select-Object -First 1` 取到正确的是**运气**——
若更正行前移、或将来再插一行同类表格行，它会**静默取错**，而输出的仍是一个合法行号，**不会报错**。

**再前一版加的过滤条件 `*不存在*` 也是无效的**：更正行在解释同一个错误时同样写了「不存在」，
所以 raw=2、filtered=2，**一个都没滤掉**——它把「靠行序」换成了「靠一个不区分的条件 + 行序」，
形式上加约束，实质没变，**而且输出仍然正确，没有任何信号提示约束没生效**。

**区分性条件的正确选法是：选一个只在目标行出现、源行不会用来给自己贴标签的词。**
`文档路径错误` 满足这一点（它是那条结论的判词，更正行不会这样描述自己）。

**判据是「行序无关性」，不是「当前取值正确」。** 把两行在内存里交换顺序后重跑：

```text
# 示意，不可直接执行：$matches / $corRow / $rest 是上文表格在内存里的变量；
# 逐字粘贴到 fresh 进程里它们都未定义，默认模式下整段静默无输出（这正是本节要防的形状）。
$errRow = ($matches | Where-Object { $_.Line -like '*文档路径错误*' }).Line
$reordered = @($corRow) + $rest + @($errRow)
```

> **已修说明（t4，2026-10-30）**：本代码块原为 `powershell` fence 且引用未定义变量，逐字粘贴运行时**默认模式静默无输出、退出码 0、`$Error.Count`=0**（已实测；只有严格模式下才报 `无法检索变量 '$matches'`）——读者会以为自己用错了。现改为 `text` fence 并在首行标注「示意，不可直接执行」；示例逻辑与上下文一字未改。

实测：`*不存在*` 在重排后**取到更正行**（返回 False）；`*文档路径错误*` 重排后**仍取到错误行**。
**「在当前状态下得出正确值」与「正确」是两个不同的性质**——前者只要不动就能维持，后者在任何状态下都维持。
本文前一版给的第三条匹配串（`这确实是我的误读`）**在报告里根本不存在**：`Select-String` 返回空，
`.LineNumber` 是 `$null`，任何依赖它的距离计算都会静默得到空值而不是数字。
**那是规则 3 的同构错误——『变异必须真的生效』的另一面是『命令必须真的跑出结果』。**
而且它比写死数字更难被发现：读者会核算术，却很少核一条命令；命令跑出空白时，
他更可能以为自己用错了，而不是怀疑命令本身。

**一个反例，说明为什么不能只改数字**：这一段的前一版曾声明「这里刻意不写具体行号」，
紧接着却写了一个具体数字，且那个数字是错的——**在它宣称"行号不可靠"的同一条论证里，
它自己依赖了一个没核的行号。** 立规矩和守规矩是两件事。

被指控的那份报告**没有机会说话**。

### 因此有三条可执行的动作（比上面的说明更有用）

1. **更正必须与原错误同址**，或至少在**原错误处**留下指向更正的指针。
   「我在别处更正过了」在功能上等于「没更正」——**读者按自己的目的读，不按你的写作顺序读。**

2. **指针必须双向。** 单向指针（错误 → 更正）只是把矛盾从「读者不知道有错」搬到
   「读者以为已改好」——**两者都是不知情，只是不知情的内容不同。**

3. **撤销要独立成行，不要行内批注。** 在逐行扫描的表格里（风险表、检查单），
   行内批注会被读成「这条**仍然有效**，只是附带说明」。**新起一行标「撤销」，
   在视觉上才是一个撤销动作。**

**这三条都不是预防措施，是「已经发生过」之后的补救格式。**
本文件不能防止你写下错误的归因；**它只能规定你在发现之后必须在哪儿写。**
