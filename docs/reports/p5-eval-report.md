### 1.1 这是什么样的任务集

本报告使用方案 §9.1 的第 1 类任务集（离线合成集），**不是**真实仓库基准：

- 每个任务有一个**必需表面集合**（相当于“通过的测试”）和一个**提案者偏好顺序**（proposer 自己并不知道必需集合）；
- 分支执行器是确定性的：候选 patch 覆盖到的必需表面越多越容易成功；完全覆盖是干净的一次通过，部分覆盖要先吃一次工具错误；参考运行固定失败，保证每个任务都有进化空间；
- mock 模型：`compose` 按 composer 渲染出的行为维度做**规则化排序**（完成度 → 工具错误 → 步数 → 交付物长度），再交给真实 composer 用 85/15 的「证据为主」混合；`reflect` 不产出 lesson；`evaluate_steps` 给中性分。它不是真实 LLM，但也不是常量，所以候选之间的取舍由行为证据驱动而不是由别名先后决定；
- 单候选路径：提案者「深化」父节点尚未覆盖的第一偏好表面（提案者不读必需集合），所以多轮血缘能把覆盖率推高；
- K 候选路径：给出 A=`[首个未覆盖偏好]`、B=`[次个未覆盖偏好]`、C=`两者合并` 三个候选；A 的先验置信度最高（0.55）、B 最低（0.45）、C 居中（0.50）。**先验在所有 run 上保持不变**，所以 run 1 与 run L 之间唯一变化的是内核积累的经验——这是 Avg/Final 能归因于学习的前提。

因此下面的结论只关于**这套合成环境里的机制**：槽位/候选分配会不会随经验改变、改变后是否更好。它不能替代真实基准（JobBench / LAB / WorkBuddy-Bench / 30 个自建仓库任务）。

### 1.2 确定性

评测配置把 `jitrl.exploration.lambda` 设为 0、`selection` 设为 `argmax`：内核里唯一未被注入的随机源（乐观探索的 `Math.random` 抽样）不再影响任何取值，其余输入都是注入的单调时钟。因此指标块是任务集与配置的纯函数，`node scripts/eval-jitrl.mjs --json` 两次运行逐字节相同（CI 断言见 `tests/e2e/jitrl-ablation.test.ts`）。计时字段不在该块内。

## 9. 如何读这份报告

- **B0 → B1**：Harness² 生命周期本身的价值（多轮血缘把部分覆盖推到完全覆盖）；
- **B1 → B2**：L1 元调度在固定探针预算下能否重排槽位组合；
- **B2 → B3**：K 候选择能否在一个候选里给出「合并修复」，从而缩短达到满覆盖所需的轮数；
- **Final − Avg**：同一套经验在第 5 次运行是否比前 5 次平均更好，即学习效率；
- **oracle 比**：离该任务在表内可达到的上限还有多远。

## 10. 本轮的诚实结论

- **Harness² 生命周期有效**：B1 覆盖率 0.889 对比静态基线 B0 0.569，绝对提升 +0.320（相对 +56.1%）；解出率 66.7% 对 25.0%。来源是单候选路径的「深化」：第 2 轮提案者补上父节点没覆盖的偏好表面，composer 把父 patch 的编辑合并回来。
- **L1 元调度在这套任务集上是零效应（如实记录）**：B2 覆盖率 0.889 与 B1 0.889 完全相同。原因可查：L1 的 4 个槽位动作在同一轮里都拿到同一个回报（每轮只评估获胜候选一次），于是 Ã 归一化后全为 0，KL 也就只剩 0.025 的极小值。也就是说，**槽位级别的信用分配需要按槽位分别计分**，而当前 orchestrator 只对获胜候选计分——这是本轮暴露的真实设计缺口，不是度量误差。
- **L2 候选选择有效**：B3 覆盖率 0.956 高于 B1 0.889（+0.067），解出率 86.7% 对 66.7%。机制：K 候选里的「合并」候选能在第 1 轮就把两个必需表面一起改到，而单候选路径要等到第 2 轮。
- **Final − Avg = +0.017（B3）**：第 5 次运行 0.972 与 5 次均值 0.956 的差。这个量很小，说明在这套 12 个任务、每个任务只有 5 次运行的环境里，经验积累只够改变少数任务的决策；它不是「学习无效」的证据，但也**不足以声称学习效率很高**。
- **A2（k）**：k=4 → 0.889，k=20 → 0.969，本轮最优 k=14（0.969）。k 太小（4）时近邻不足以形成稳定优势，KL 直接掉到 0.000；k 变大后覆盖率与 KL 同时上升。注意 k 也只改变**检索宽度**，不改变打分口径。
- **A3（β）**：β 从 0.5 到 4，KL 均值从 0.009 升到 0.102，**单调上升**（符合 §6.4 的闭式解）；而 Avg 在所有 β 上都是 0.956，即**温度只改变分配幅度、不改变最终选中的槽位组合**。这符合预期：β 是 KL 温度，不是评分函数。
- **安全**：13 个条件共 3840 次 invariant 提案，三类 invariant 泄漏与 canary 泄漏合计 **0**（要求为 0，CI 已断言）。
- **不能从本报告得出的结论**：真实仓库任务上的收益、跨任务泛化的强度、真实 LLM judge 的影响、embedding 检索是否更好。这些需要 §9.1 的第 2/3 类任务集，本轮未做。
