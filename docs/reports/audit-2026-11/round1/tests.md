# Audit scope: test suite quality

Scope: `tests/` (unit + e2e + fixtures/host-smoke helpers) vs `src/`. Method: full file enumeration, grep census of assertion idioms, spot reads of ~20 test files, symbol-level import tracing for every `src/` module, and full reads of the claimed gates (`tests/unit/p62/*`, `tests/unit/meta/no-work-dependency.test.ts`), `tests/e2e/fixtures.ts`, and three representative e2e tests.

## Quantitative summary (counts: total test files, weak-assertion hits with file examples, untested src files list)

- **Test files**: 163 `*.test.ts` (140 under `tests/unit/`, 23 under `tests/e2e/`) plus 19 fixture/helper `.ts` files (e.g. `tests/e2e/fixtures.ts`, `tests/unit/memory-bridge/mocks/mock-mcp.ts`, `tests/unit/meta/work-path-scanner.ts`). ~709 `describe()` blocks, 2,841 `it/test` declarations, **11,858 `expect()` calls** (~4.2 asserts per test).

Spot reads show most are optional-chaining *narrowing guards* (`const selected = ...; expect(selected).toBeDefined();` followed by property assertions), not standalone verdicts.
  - `toBeTruthy`: **4**, all in `tests/unit/p62/evidence-gates.test.ts:668-674` (opaque env-var presence: PATH/ComSpec/SystemRoot — value content not assertable, acceptable). `toBeFalsy`: **0**.

## Findings

### [TEST-1] DSH host-boundary protocol layer (model.ts + clients.ts, ~1000 lines) has zero automated tests (P1)
- File: src/dsh-bridge/model.ts:518; src/dsh-bridge/clients.ts:77
- Evidence: `export function createLlmModelAdapter(` (model.ts:518) — grep for `createDshModel|chunkTypeOf|usageToTokens|finishReasonOf|toDshMessages|describeDshFailure|readDshTools|listDshTools|toMcpToolResult|createToolsBackedMcpClient` across `tests/**` returns nothing. Every e2e/unit test injects the scripted `IModelAdapter` from `tests/e2e/fixtures.ts:142` (`createScriptedModel`). The file itself documents a nontrivial wire contract: "A stream ALWAYS ends in exactly one 'finish' chunk ... a stream that throws before any finish chunk ... must not be reported as one" (model.ts:5-15 header).
- Analysis: model.ts encodes the real host LLM chunk protocol (block-start/text-delta/reasoning-delta/tool-call-delta/usage/finish), finish-reason mapping, token-usage extraction, and a failure taxonomy; clients.ts maps DSH tool surfaces to MCP results. These are the ONLY modules swapped in when the plugin runs inside the real host — everywhere else the suite exercises real code. A regression here (e.g. a finish chunk misclassified, usage dropped, partial stream reported as settled) would pass all 163 test files green. The only exercising path is `scripts/host-smoke/run.mjs` against an installed DSH runtime, which the repo itself gates behind authorization and which is not part of `vitest run`.
- Fix: add pure unit tests for the exported, dependency-free helpers in model.ts/clients.ts (`chunkTypeOf`, `usageToTokens`, `finishReasonOf`, `toDshMessages`, `describeDshFailure`, `toMcpToolResult`, `snapshotJsonValue`) using recorded chunk sequences, including the "stream throws before finish" and "duplicate finish chunk" edge cases the header declares as host facts; drive `createLlmModelAdapter`/`createToolsBackedMcpClient` with a fake `ctx.llm.stream` async iterable — no real host needed.

### [TEST-2] E2E suite never exercises a real branch execution; probe results are canned by ScriptedRunner (P2)
- File: tests/e2e/fixtures.ts:214 (createScriptedRunner), tests/e2e/fixtures.ts:760 (buildE2E)
- Evidence: `/** Scripted branch executor: the reference run fails, patched candidates recover */ ... return { status: 'succeeded', steps: [...], deliverable: { content: 'recovered: ...' } }` — the runner returns hand-built `ProbeExecutionResult` objects; it never executes the mounted patch in an isolated context. Header of fixtures.ts: "No network, host runtime, sandbox or real LLM is involved."
- Analysis: the orchestrator, composer, proposer, reflector, memory bridge, policies and taxonomy are all REAL in e2e (verified: `tests/e2e/memory-write-path.test.ts`, `tests/e2e/jit-control.test.ts` drive `createEvoHarnessPlugin` with real modules), which is good. But the seam between "patch selected" and "probe result observed" — mount of surfaces into an actual executing branch, trajectory collection from a live run — is only covered by `tests/unit/dsh-bridge/agent-loop-executor.test.ts` (with a hanging planner, not a real tool loop) and the fake-host `tests/e2e/host-smoke/contract-smoke.test.ts` (in-process waterfall, "NO real DSH host"). The composition "real agent-loop executor + real seam manager + real orchestrator" is never run in the automated suite. The e2e suite is green by construction over any regression in that composition.
- Fix: add one e2e scenario that wires `createAgentLoopExecutor` (scripted model + scripted in-memory tools) as the `runBranch` behind the real `createCordisSeamManager`, so the canned `ProbeExecutionResult` is replaced by one produced by a real executor run; assert the composed patch actually mounts (not just that a scripted result says so). `contract-smoke.test.ts` already has the waterfall fixture to copy.

### [TEST-3] Wall-clock performance bounds will flake on loaded CI (P2)
- File: tests/unit/orchestrator/concurrency.test.ts:584; tests/unit/jitrl/experience-store.test.ts:516
- Evidence: `expect(elapsedMs).toBeLessThan(200);` (concurrency, after 4 probes of ~100 ms each — 2x headroom on real timers); `expect(elapsed).toBeLessThan(25);` (experience-store single query bound, 25 ms wall clock, comment: "Warm the path up, then assert a single query stays far below the bound").
- Analysis: both assert scheduler/IO *speed* with `Date.now()` on shared runners. The concurrency assertion has only ~100 ms slack over the work itself; a GC pause or co-tenant CPU steal on CI pushes it over with no behavioral change. The 25 ms store-query bound is tighter and measures a non-functional property the store's contract does not promise. `vitest.config.ts` already documents the repo's own philosophy that "load is the variable, not the test" — these two assertions contradict it.
- Fix: keep the correctness assertions (`maxActive === 4`, `candidateExecutions` length, `scored.length <= 8`) and demote the timing bounds to `toBeGreaterThanOrEqual` lower bounds (proving overlap happened) or log-only; if a perf regression guard is truly wanted, mark it `describe.skipIf(process.env.CI)` with a generous multiplier.

### [TEST-4] Ledger-event module contains dead, untested exports (P3)
- File: src/ledger/ledger-event.ts:22
- Evidence: `export function generateEventId(callId: string, phase: LedgerPhase): string` and `export function isMandatoryAuditOnlyOutcome(outcome: ExecutionOutcome): boolean` — grep over `src/` and `tests/` finds zero callers (only `createUsageLedgerEvent` is used, by `reservation-manager.ts`, and then only indirectly through `reservation-manager.test.ts`).
- Analysis: two exported functions with zero callers are either dead code awaiting use or leftovers from a refactor; either way nothing pins their behavior, and the barrel (`src/ledger/index.ts`) still publishes them as supported API surface.
- Fix: delete them, or give them a direct unit test if they are about to be consumed; add a dead-export check to the structural-debt gate if the repo wants this class of rot caught mechanically.

### [TEST-5] Nested vitest run inside a meta-test is heavy and doubly fragile (P3)
- File: tests/unit/meta/no-work-dependency.test.ts:396-404
- Evidence: `const result = spawnSync(process.execPath, [VITEST_ENTRY, 'run', GATE_TEST], { cwd: REPO_ROOT, ..., timeout: 600_000, maxBuffer: 64 * 1024 * 1024 });` invoked by three separate tests ("exits NON-ZERO when the fixture manifest is missing", "when the REQUIRED artifact is missing", "when a fixture byte drifts").
- Analysis: the approach is fail-closed and honest (it measures that the gate actually fails rather than grepping for a keyword — commendable), but it spawns a full vitest process three times inside a vitest worker, which serializes a large fraction of the suite's runtime behind one file, can contend for the shared `work/`/esbuild cache with parallel workers, and inherits a 10-minute timeout that can hide a wedged CI runner. It is also sensitive to the vitest entry path (`node_modules/vitest/vitest.mjs`) moving between versions.
- Fix: keep the technique but (a) reduce to one child run with all three mutations, or reuse the already-imported gate module in-process for the manifest/digest cases and keep exactly one child-process case as the end-to-end proof; (b) assert the vitest entry exists first so the failure mode is a named error, not a spawn ENOENT.

### [TEST-6] Small tail of standalone no-throw assertions that cannot fail meaningfully (P3)
- File: tests/unit/dsh-triggers.test.ts:284; tests/unit/integration/p2-wiring.test.ts:131; tests/unit/jitrl/jit-active-policy.test.ts:448
- Evidence: `expect(() => listeners.get('agent/status')?.({ status: 'idle' })).not.toThrow();`, `expect(() => JSON.stringify(plugin.jitrl)).not.toThrow();`
- Analysis: these pin "does not crash" but would stay green if the handler did nothing at all. They are few (19 `not.toThrow` across 11,858 expects) and usually accompanied by neighboring behavioral assertions, so the risk is minor — but the serialization ones assert a property that is almost guaranteed for any plain object.
- Fix: replace serialization no-throw checks with a shape assertion on the serialized result (e.g. `expect(Object.keys(JSON.parse(JSON.stringify(status)))).toContain('executionProfile')`), and pair event-dispatch no-throw checks with a spy assertion that downstream state changed.

## Positive verifications (genuinely strong tests, verified)

1. **`tests/unit/meta/no-work-dependency.test.ts` — real discrimination, not tautology.** It plants the exact defect (a verbatim copy of the code that shipped in HEAD 97e38db, including the one-indirection shape where the path is built in one statement and read in another), asserts the scanner reports it at the right lines, asserts ZERO findings on a clean tree (so the positive case cannot be a scanner that flags everything), treats unresolvable roots as findings (fail-closed), checks the allowlist in BOTH directions (a stale pin fails, a new unpinned read fails, every pin needs a >120-char reason), and *measures* (child vitest run) that the gate exits non-zero on a missing manifest / missing artifact / drifted sha256 rather than trusting a keyword. The scanner itself documents its declared static-analysis boundary and how the meta-test compensates for it.
2. **`tests/unit/p62/evidence-gates.test.ts` — every gate tested in both directions with real fixtures.** Encoding-policy gate is exercised against real throw-away git repos (tracked vs untracked identical bytes, CRLF/BOM/binary violations, blanket-renormalise, CLI exit codes); the attestation CLI is verified through re-verification, tampering with every digest field (composite, binding, algorithm, encoding, mode, blobId, bytes, roots, base tree/ancestry), and the cross-OS parity rule fails on differing commits, non-hex digests, fileCount=0, and <3 platforms. `afterAll` even asserts the fixture left no `pr1-policy-commit-*` refs or worktrees behind (line 193). The sibling p62 gates (`build-freshness`, `clean-tree-gate`, `docs-gate-j1`, `negative-result-assertions`, `commit-attestation`) follow the same fail-both-directions discipline — none are tautologies.
3. **`tests/unit/memory-bridge/isolation-and-firewall.test.ts` — the opposite of mock-testing-mock.** The suite *deliberately weakens* the mock (`graphEntityServer`/`vectorFactServer` with `enforceNamespace: false`, header: "namespace-blind mocks to prove the isolation is enforced client-side, not by the backend") so the real `createMemoryBridge` must do the filtering. `tests/e2e/memory-write-path.test.ts` goes further and ships a *strict* backend with no fallback because "the shared e2e fixtures deliberately fall back, which is exactly the shape that cannot prove isolation" (header, lines 15-16). The mocks (`tests/unit/memory-bridge/mocks/mock-mcp.ts`) are passive recorders with configurable failure modes (`rejectWrites`, `hangTools`); consumers assert the calls the REAL drivers made (`drivers.test.ts` `assertCommit(call, server)` on recorded `MockCall`s), never the mock's own logic.
4. **`tests/e2e/jit-control.test.ts` — regression test pinned to a documented pre-fix defect.** The header records the exact witness of the bug (static `kernel.config.enabled` read instead of the volatile switch: "K candidate calls=2 — STILL CALLED ... experience store delta=4 — STILL GREW") and the assertions (candidate-call counters, store delta, mirror suppression) all fail against that code, covering off→on revival, dispose permanence, and the off-while-in-flight race.
