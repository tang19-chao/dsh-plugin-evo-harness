# Audit scope: build, CI, eval gates

## Verified facts summary (2-5 lines)

Read-only cross-audit of build.mjs/build-manifest.mjs, all scripts/eval gates (check-clean-tree, check-encoding-policy, check-attestation-target, final-attestation, mutation-gate, guarded-regression, negative-result-diag, smoke-build, compare-platform-digests, metering-coverage, lib/git-objects.mjs, pr4a-*/rev6-*), scripts/host-smoke/*, scripts/fixtures/ledger/*, .github/workflows/ci.yml, vitest.config.ts, tsconfig.json, cordis.patch.yml, .gitattributes/.gitignore and package.json wiring. **No P0 found: the attestation chain is genuine, not self-referential** — the committed record (`docs/reports/final-attestation.json`) attests ancestor `1b7920e` (4 commits behind HEAD `4b5b92c`), digests are computed from object-database blob bytes (`git cat-file --batch`), `bindingSha256` binds commitId+treeId+composite, and `--verify` recomputes per-file blobId/mode/bytes/sha256/encoding from the object DB, so any tampering with attested bytes or the record fails (and history rewrites break the T7 ancestry check). No tautology found in mutation-gate, check-clean-tree, negative-result-diag `--assert` or compare-platform-digests; every documented `check:*` gate is wired into a ci.yml job and the README's CI claims match ci.yml exactly. The findings below are real but secondary: two smoke-gate coverage gaps, a build-stamp blind spot for bundled dependencies, a typecheck coverage gap, and several P3 wiring/portability issues.

## Findings

### [GATE-1] smoke-build asserts the named-export surface but never the DEFAULT export the host actually loads (P2)
- File: scripts/eval/smoke-build.mjs:61-66 (and 187-216); cordis.patch.yml:3-5
- Evidence: `export const REQUIRED_EXPORTS = Object.freeze(['apply','createEvoHarnessPlugin','PLUGIN_NAME','Config']);` — the gate then only checks `missing = REQUIRED_EXPORTS.filter((name) => !(name in namespace))` and the types of `apply`/`createEvoHarnessPlugin`. cordis.patch.yml (the host mount layer) declares: "DSH resolves the entry by the Node-resolvable package name below … then calls its default `{ name, inject, Config, apply }` export."
- Analysis: ci.yml's build step claims the gate "asserts the public surface", but the surface the host consumes is the **default export** (`export default plugin` at src/index.ts:3518, shape `{ name, inject, Config, apply }`). If `export default plugin` were dropped or reshaped (e.g. `name` typo'd so the Node-resolvable name no longer matches package.json), smoke-build stays green while the cordis.patch.yml mount path breaks — the exact "builds but cannot be consumed" class the gate exists to catch. The ESM namespace object does expose `default`, so the check is one line away.
- Fix: extend the smoke gate to assert `namespace.default` is an object whose `name === 'dsh-plugin-evo-harness'` and whose `inject`/`Config`/`apply` match the named exports (mirroring cordis.patch.yml's contract), and add `default` semantics to REQUIRED_EXPORTS checking.

### [BUILD-1] build-stamp freshness is blind to bundled dependency bytes — a dep bump without rebuild passes as "fresh" (P2)
- File: scripts/build-manifest.mjs:94 (`entry.name.endsWith('.ts')` file set = `src/**/*.ts` only); scripts/build.mjs:42-51
- Evidence: build.mjs bundles with no `external`/`packages` field, so `@deepseek-ai/schemastery` (package.json dependencies, line 63) is **inlined** into `lib/index.js`; `buildStamp()` computes `srcTreeSha256` over "src/**/*.ts (recursive)" only (algorithm block, build-manifest.mjs:190-197).
- Analysis: `computeBuildStatus()` compares the current `src/**/*.ts` digest and the artifact sha256 against the recorded stamp. A `pnpm update @deepseek-ai/schemastery` (or any lockfile change) followed by a smoke test **without rebuilding** leaves both unchanged: src tree identical, old artifact identical to its own stamp → `stale: false`. Since the dependency's bytes are part of the artifact identity (it is bundled, not external), the stamp's claim "an expired artifact can no longer pass" (build.mjs header) holds only for src edits. The recipe freezes the file set, so fixing this requires a schema-version bump.
- Fix: extend the stamp recipe (schemaVersion 1.1.0) to fold in a digest of the resolved dependency bytes (or at minimum the pnpm-lock.yaml + esbuild version hashes), and refuse a stamp whose schemaVersion the gate does not know.

### [BUILD-2] `pnpm run typecheck` covers only src/ and tests/ — ~340 KB of shipped TypeScript under scripts/ is never typechecked (P2)
- File: tsconfig.json:31-34
- Evidence: `"include": ["src/**/*.ts", "tests/**/*.ts"]` (only one tsconfig exists at the root).
- Analysis: `scripts/eval/jitrl-eval-lib.ts` (198 KB), `pr4a-five-arm-lib.ts` (75 KB), `pr4a-report.ts` (43 KB), `pr4a-stats.ts` (23 KB) and `scripts/fixtures/ledger/*.ts` (imported by `tests/unit/ledger/offline-fixtures.test.ts`) are transpiled by esbuild/vitest, neither of which typechecks. A type-level drift between the eval libs/fixtures and `src/ledger/types.ts` (e.g. a renamed `ModelRateCard` field) is invisible to `tsc --noEmit` and to CI until it fails at runtime (or never fails, for type-only positions). The README sells typecheck as the "full static typecheck"; it is full only for src/tests.
- Fix: add `"scripts/**/*.ts"` to tsconfig `include` (with `.d.mts` neighbours still excluded by default), or ship a second `tsconfig.scripts.json` run in the `typecheck` script and in the CI Typecheck step.

### [CI-1] metering-coverage "static gate" has no named runner — CI coverage exists only through one unit test that could be refactored away silently (P3)
- File: scripts/eval/metering-coverage.mjs (whole file); package.json:33-55 (no script); .github/workflows/ci.yml (no step)
- Evidence: `DEFAULT_ALLOWLIST` gate with strict both-direction counting, but the only invocation anywhere in CI is `tests/unit/ledger/metering-coverage.test.ts` spawning it as a child process against the real tree; docs/reports/p3-b-adapter.md §3 documents it as "静态门：`scripts/eval/metering-coverage.mjs`（新增）" and reports invoke it directly (`node scripts/eval/metering-coverage.mjs`).
- Analysis: unlike every other documented gate (check:docs/encoding/clean-tree/build-smoke/negative-result/mutation/guarded-regression all have package.json scripts and ci.yml steps), metering-coverage is reachable in CI only as a side effect of one vitest file. Deleting or renaming that test file removes the gate from CI without any CI-visible change — the same "documented gate that CI never executed" defect class the repo itself called out for guarded-regression before wiring it (ci.yml:127-129).
- Fix: add `"check:metering": "node scripts/eval/metering-coverage.mjs"` to package.json and one step to the ci.yml `verify` job (or cite the unit test as the canonical runner in p3-b-adapter.md so the wiring is discoverable).

### [GATE-2] smoke-build's freshness check is self-fulfilling in the default (CI-invoked) mode (P3)
- File: scripts/eval/smoke-build.mjs:94-100 (build) and 128-140 (freshness)
- Evidence: default mode runs `execFileSync('pnpm', ['run', 'build'], …)` — which itself writes a fresh `lib/build-stamp.json` from the current tree — and then immediately calls `computeBuildStatus({ cwd })` and fails on `freshness.stale`.
- Analysis: in default mode the stamp being verified was just written by the same invocation against the same bytes, so `src-tree-mismatch`/`artifact-mismatch` can only fire on a concurrent src edit inside a millisecond window or a corrupt stamp write. The check's real discriminating power lives in `--status` and `--skip-build` modes, which ci.yml never runs (both CI invocations, verify:121 and the Windows fingerprint leg:258, use default mode). The gate is not wrong, but the CI evidence "refuses a stale artifact" (ci.yml:115-119 comment) is much weaker than the comment implies — CI would catch a stale artifact only via the rebuild itself, not via the freshness comparison.
- Fix: either run `--skip-build` against a pre-built artifact in one CI leg (so the comparison judges a stamp not written by the same process), or reword the ci.yml comment to say freshness has teeth locally/`--status`, not in the default CI mode.

### [CI-2] verify-readme-counts cleanup deletes a root test-results.json it never consumed (P3)
- File: scripts/verify-readme-counts.mjs:97-107
- Evidence:
  ```js
  if (rootReportConsumed && fs.existsSync(rootTestResultsPath)) { … unlink … }
  // Safety check: ensure repository root has no lingering test-results.json
  if (fs.existsSync(rootTestResultsPath)) { … unlink … }
  ```
- Analysis: the header contract says "A root `test-results.json` that was consumed is deleted as before. External `--report` files are never deleted." The second, unconditional `if` deletes the root report even when the gate consumed `--report <other>` or ran `--docs-only` — destroying an unconsumed (possibly freshly produced, wanted) report. Not a CI problem (CI's gate consumes the root file by design), but it contradicts the documented cleanup invariant and can confuse a local run.
- Fix: gate the safety-check deletion on `rootReportConsumed` (or drop it; the first branch already covers the consumed case).

### [CI-3] Node engines floor (>=20.19.0) is never measured on any CI leg (P3)
- File: package.json:25 (`"node": ">=20.19.0"`); .github/workflows/ci.yml:50,157,210,295,384,469,529 (Node '22' everywhere, Node '24' only in node24-compat); scripts/build.mjs:47 (`target: 'node20'`)
- Evidence: the matrix tests Node 22 (all gates) and Node 24 (compat job); no job installs Node 20.x.
- Analysis: the supported-version line "Node >= 20.19" is an assumption at its floor while the repo's own standard for such claims is "measured, not assumed" (the node24-compat job exists precisely for that reason at the top end). Node 20 also reached EOL in April 2026, so the floor is both untested and unsupported upstream.
- Fix: add a Node 20 leg (e.g. extend node24-compat into a version-compat matrix `['20.19', '24']`), or lower/raise `engines` to the versions actually measured.

### [CI-4] host-smoke runner timeout kill does not reap the in-host process tree; the surviving-pid check only watches the direct child (P3)
- File: scripts/host-smoke/run.mjs:240-243 (`child.kill()` on deadline), 262-273 (`pidAlive(pid)`), 470-482; scripts/host-smoke/in-host.mjs:180-194 (spawns the MCP backend via `spawnProcess`); tests/e2e/host-smoke/mcp-backend-server.mjs (no stdin-`close` handler, no explicit exit)
- Evidence: on timeout the runner calls `child.kill()` (SIGTERM / TerminateProcess on the single in-host pid) — no process-group/taskkill tree kill; afterwards `pidAlive(spawnOutcome.pid)` checks only that pid, and `checkTimeoutAndUnload` can only read a result.json the killed child never wrote.
- Analysis: if the in-host process is killed while the MCP backend grandchild is alive (e.g. inside the 2 s `hostsmoke_slow` tool), the grandchild is orphaned: on Windows TerminateProcess does not kill children, and on POSIX only the direct child is signalled. Severity is bounded — the fixture backend's stdio pipes EOF when the parent dies, so it exits once its event loop drains — but the runner's boundary check ("a run must leave no lingering child process") structurally cannot observe this class of leftover.
- Fix: spawn the in-host child detached with a platform-appropriate tree kill (POSIX: `process.kill(-pid)`; Windows: `taskkill /T /F`), and/or have the backend fixture exit on stdin `close`.

### [CI-5] run.mjs header note about rc2 overwrite protection is stale — the guard it says is missing has existed since t33 (P3)
- File: scripts/host-smoke/run.mjs:30-35 vs scripts/host-smoke/report-path.mjs:47-50
- Evidence: run.mjs NOTE (t31): "The guard in ./report-path.mjs currently protects rc1 only (`FROZEN_RC1_RELATIVE`); `RC2_RELATIVE` is exported but not consulted by the guard, so nothing stops an accidental write to rc2 except this note." — but report-path.mjs (t33) defines `FROZEN_REPORT_RELATIVES = Object.freeze([FROZEN_RC1_RELATIVE, RC2_RELATIVE])` and `inspectFrozenReportTarget` consults the whole list.
- Analysis: the shipped header contradicts the shipped guard. It understates the actual protection and invites someone to re-implement a check that already exists (the same file's own comment documents t33 as the fix for exactly the t31 finding). Doc drift only; behaviour is correct.
- Fix: delete the t31 NOTE from run.mjs (or replace it with a pointer to `FROZEN_REPORT_RELATIVES`).

## Positive verifications

1. **The attestation chain binds digests to a commit and is not self-referential; it fails on tampering.** `lib/git-objects.mjs` hashes raw blob bytes from the object database (`git cat-file --batch`, never `fs`), `compositeSha256` = SHA256 of sorted `path:blobSha256` lines over roots `src/tests/scripts`, `bindingSha256` = SHA256 over `commit <id>\ntree <id>\ncomposite <c>`. `--verify` recomputes the manifest at the *recorded* commit id and compares per-file blobId/mode/bytes/sha256/encoding/exception plus the algorithm block (`compareManifests`); the committed record attests `1b7920e` while HEAD is `4b5b92c` (no self-coverage), `docs/` is outside the digest roots, and CI layers three independent checks: plain `attest:verify` (verify job), per-commit target binding T0–T8 + R-06 record-source binding (`attestation-target` job, including a mechanical self-reference assertion against `github.sha`), and a 3-OS parity job that regenerates fresh records with `--ref/--expect-commit github.sha` on ubuntu/macos/windows and compares them with the closed-set rule. Forgery would require rewriting git history (content-addressed blob ids), which simultaneously breaks the record's commitId and the T7 `merge-base --is-ancestor` check.
2. **The mutation gate can fail and is not a tautology.** `mutation-gate.mjs --run` requires, per mutant: an all-green baseline on the same throwaway copy (`baseline-no-tests-collected` fails a 0-test run), a proven sha256 change (`mutation-did-not-change-sha`), `mustRed` test *names* ⊆ actual red names (skips never count as kills), a restore witness, a zero-residue re-hash of the real worktree targets, and mutants applied only under `os.tmpdir()`; an empty `--only` selection yields `ok:false` (fail-closed).
3. **Every documented check gate is wired into CI and the README's CI claims match ci.yml exactly.** check:clean-tree (before install, `--require-tracked` test inputs), check:encoding, typecheck, the eval CLI, negative-result `--assert`, `attest:verify`, the full vitest suite, check:docs, and smoke-build run in `verify`; guarded-regression plus both `node --test` suites (deliberately outside vitest's `*.test.*` glob — verified the glob cannot match `*.node-test.mjs`) in their own job; attestation-target, mutation-gate and node24-compat as independent jobs; fingerprint matrix [ubuntu, macos, windows] + parity job with `--expect-commit`. All actions are SHA-pinned with `persist-credentials: false`, and full history is fetched exactly where ancestry/`HEAD~1` resolution is required.
4. **verify-readme-counts really verifies README numbers, with fail-closed report integrity.** It refuses reports with failed/pending assertions, then enforces J-1 (`success` boolean, `numFailedTestSuites`, `numTodoTests` required to exist and be clean, `unhandledErrors` when present), R-04 root attribution (every file under /tests/unit/ or /tests/e2e/) and three-way count closure before comparing README summary/unit/e2e/total rows against the actual run; the Configuration reference is validated against the REAL defaults compiled from src/config.ts + src/dsh-bridge/model-config.ts by esbuild (never a hand-copied table), failing on missing/stale/drifted leaves.
5. **cordis.patch.yml matches the implemented eight surfaces.** Its `enabledSurfaces` list (system_prompt, guardrails, memory, tool_guidance, skills, scripts, subagents, plugins) is exactly `HARNESS_COMPONENT_KEYS` (src/types/contracts.ts:71-80) and the `SURFACE_HOST_METHOD` map (src/cordis-seams/eight-surfaces.ts:55-63); `triggerMode: auto_fallback` and the `modelRoute` block correspond to the documented schema/defaults, and the patch's package name matches package.json `name`.
6. **The last commit's `--check` portability fix is genuinely portable.** commit 4b5b92c fixes the environment-dependent test by creating a throwaway installation (platform-correct executable placeholder + `resources/app.asar/package.json`) and pinning discovery via `HOSTSMOKE_DSH_HOME`, which `locateDshHost` honours first on every platform — the readiness assertion now tests the logic, not the machine.
7. **check-clean-tree and check-encoding-policy fail closed with validated inputs.** The clean-tree allowlist is validated against protected paths (`src/tests/scripts/package.json/pnpm-lock.yaml/.gitattributes`) before use and re-checked after matching; the encoding gate reads the policy from the ATTESTED COMMIT (`git check-attr --source`, tree-parser fallback only for the exact "unknown option" failure), refuses blanket renormalisation rules, and inspects every tracked blob (CRLF/lone-CR/BOM/NUL classified in `classifyBytes`) — matching the committed `.gitattributes` policy, whose narrow declarations (including `tests/fixtures/encoding/** -text`) and un-anchored-vs-anchored `.gitignore` patterns (`/lib/` so `scripts/eval/lib/` stays tracked) are both correct.
