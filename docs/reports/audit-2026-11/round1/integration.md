# Audit scope: cross-module integration

## Verified facts summary
`apply()` → `createEvoHarnessPlugin()` builds everything synchronously: `parseEvoHarnessConfig` → `buildOrchestratorDeps` (host adapter resolution → memory bridge → seam manager → active policy (L1-wrapped when JitRL enabled) → harness2 proposer/composer/reflector → surrogate scorer → taxonomy → (Jit-wired) offline dreamer) → `createEvoHarnessOrchestrator`, then registers `/evo` via `ctx.commands.register` (+ structural fallback), subscribes the three verified DSH trigger events, and async-resolves `ctx.llm`/`ctx.tools` collaborators into a `holder` object. Metering is enforced at 7 dedicated `createMeteredModelAdapter(stage)` boundaries; JitRL surfaces share one `JitRuntimeControl`; reward/provenance/schema versions are single-sourced in `src/jitrl/reward-contract.ts` + `experience-store.ts`. The DSH auto-resolved model and branch executor are collected but never consumed (INT-1); the perturbation-grid config leaf set and the dreamer's grid reader disagree (INT-3); `logging.*` is dead config (INT-5).

## Findings

### [INT-1] DSH auto-resolved model and branch executor are dropped: `CollaboratorHolder` forwarding is dead code (P0)
- File: src/index.ts:2350-2358 (helpers defined, zero call sites), src/index.ts:2120-2135 (proposer/composer/reflector built from `missingModelAdapter()`), src/index.ts:2202 (runBranch chain), src/index.ts:2921-2926 (holder filled, never read); counterpart src/dsh-bridge/index.ts:282-284, 313-331 (real model + same-process executor built here)
- Evidence:
  - src/index.ts:2334-2344 documents the intent: "The orchestrator therefore receives stable FORWARDING collaborator objects whose target is replaced once detection settles".
  - `grep -n "forwardingModel\|forwardingBranch" src/index.ts` → only the two definitions at 2350/2356; **no call site exists anywhere in src or tests**.
  - src/index.ts:2120: `const model = options.deps?.proposer === undefined ? options.model ?? missingModelAdapter() : undefined;` — on a real host (`options.model` absent, model resolved from `ctx.llm` via `resolveDshCollaborators`, default `resolveDshCollaborators: true`) every harness2 stage gets `missingModelAdapter()`, whose `complete()` throws `'dsh-plugin-evo-harness: no model adapter was injected'`.
  - src/index.ts:2202: `runBranch: options.deps?.runBranch ?? options.runBranch ?? agentExecutor?.runBranch ?? unconfiguredBranchExecutor(now)` — with no `options.runBranch`/`options.agentLoop`, every probe runs the loud-failure executor (`'no branch executor was injected; the host must supply options.runBranch'`), even though `resolveDshCollaborators` (src/dsh-bridge/index.ts:320-327) built a working same-process executor.
  - src/index.ts:2921-2926 writes `holder.model = resolvedCollaborators.model; holder.runBranch = resolvedCollaborators.runBranch;` — nothing ever reads `holder` afterwards (only assignments at 2509/2511/2921/2924; `plugin.collaborators` exposes the promise for external readers only).
- Analysis: the documented deferred-collaborator design is disconnected. On a real DSH host that relies on auto-detection, every `/evo` run silently degrades to `no_probe` (proposal calls throw per-slot; the reference probe returns the loud-failure trajectory) while the plugin diagnostics claim "model route in effect: qodercn/dfmodel …". All e2e tests inject `options.model`/`options.runBranch` directly (tests/e2e/plugin-entry.test.ts:37,98,213), so the broken path has zero coverage. This is a broken producer→consumer data flow, not a missing feature.
- Fix: in `buildOrchestratorDeps`, wire the stage collaborators through the holders: `model: forwardingModel(holder, () => missingModelAdapter())` for proposer/composer/reflector and `runBranch: forwardingBranch(holder, unconfiguredBranchExecutor(now))` in the deps chain (the helpers already exist at src/index.ts:2350-2358). Alternatively make `collaborators` resolution synchronous-before-orchestrator-construction where a context is available, or rebuild the run path after `holder` settles. Add an e2e test that mounts with a fake `ctx.llm` and no `options.model` and asserts `probesRun > 0`.

### [INT-2] `model as IModelAdapter` casts `undefined` into composer/reflector when `deps.proposer` is injected (P1)
- File: src/index.ts:2120 (ternary), src/index.ts:2126-2135 (composer/reflector construction); counterpart src/harness2/composer.ts:571, src/harness2/reflector.ts:572 (`createMeteredModelAdapter(options.model, …)`)
- Evidence:
  - src/index.ts:2120: `const model = options.deps?.proposer === undefined ? options.model ?? missingModelAdapter() : undefined;`
  - src/index.ts:2126-2131: `const composer = options.deps?.composer ?? createAnonymousComposer({ model: model as IModelAdapter, … })` and the same cast for `createEvidenceReflector`.
  - src/harness2/composer.ts:571: `const model = createMeteredModelAdapter(options.model, 'compose', options.metering);` → `call()` executes `await inner.complete(request)` with `inner === undefined` → `TypeError: Cannot read properties of undefined (reading 'complete')`.
- Analysis: when a host injects `deps.proposer` but not `deps.composer`/`deps.reflector`, `model` is forced to `undefined` even if `options.model` was provided, and the cast hides it from `tsc`. The documented override combination (custom proposer + default composer) fails at run time with a raw TypeError instead of the loud `missingModelAdapter()` error, and the explicitly supplied `options.model` is silently discarded.
- Fix: resolve the model independently of the proposer: `const model = options.model ?? missingModelAdapter();` (keep `missingModelAdapter` only when no model exists), or pass `options.model ?? missingModelAdapter()` explicitly into `createAnonymousComposer`/`createEvidenceReflector` instead of the shared ternary result. Add a unit test: `createEvoHarnessPlugin({ deps: { proposer }, model })` must produce a composer whose judge calls reach `options.model`.

### [INT-3] `jitrl.dream` perturbation grid: two dimensions unreachable from config, one documented leaf dead (P2)
- File: src/dream-rsi/offline-dreamer.ts:349-356 (`resolveJitPerturbationGrid` reads `candidateJitKs`/`candidateJitSimilarityThresholds`), src/config.ts:198-207 (`JitRlDreamConfig`), src/config.ts:597-602 (`JIT_DREAM_KEYS`); counterpart README.md:295-296
- Evidence:
  - src/dream-rsi/offline-dreamer.ts:352-353: `const ks = finiteIntegerGrid(config.candidateJitKs); const thresholds = finiteUnitGrid(config.candidateJitSimilarityThresholds);`
  - src/config.ts JIT_DREAM_KEYS allows only `['driftRho','hyperparamPerturbation','candidateJitBetas','candidateJitLambdas']` — a host writing `jitrl.dream.candidateJitKs` is rejected with `unknown_key`, so `ks`/`thresholds` can never come from configuration and are pinned to `DEFAULT_JIT_KS`/`DEFAULT_JIT_SIMILARITY_THRESHOLDS` (offline-dreamer.ts:277,370-373).
  - offline-dreamer.ts:354-356: "The legacy lambda grid is reported verbatim (or as the built-in default) but is never consumed" — yet `candidateJitLambdas` is a validated leaf (config.ts:205,1338-1344) and README.md:296 documents it as "Candidate lambda grid **drawn from when generating policies**".
- Analysis: stringly-typed config contract drift that TypeScript cannot catch: the consumer (`JitPerturbationConfig`) expects two keys the frozen schema forbids, and documents one key the consumer ignores. A host tuning `candidateJitLambdas` gets no effect (deliberate per `JIT_IGNORED_DIMENSIONS`, offline-dreamer.ts:289-300, but the README claims otherwise), and the k/threshold sweep axes are dead from configuration.
- Fix: either add `candidateJitKs`/`candidateJitSimilarityThresholds` to `JitRlDreamConfig` + `JIT_DREAM_KEYS` (+ README rows), or remove them from `JitPerturbationConfig` reads; mark `candidateJitLambdas` as deprecated in the schema comment and correct the README row to "accepted for compatibility; not swept since P6 PR5" (the `pnpm run check:docs` gate walks defaults, not semantics, so it cannot catch this today).

### [INT-4] `/evo` can be registered twice when a host exposes both command registrars (P2)
- File: src/index.ts:3276-3293 (ctx.commands.register path) and src/index.ts:3295-3318 (registerCommand/command/addCommand fallback)
- Evidence:
  - src/index.ts:3273-3277: "DSH's own command service takes precedence: ctx.commands.register …" — but the fallback block is an independent `if`, not an `else if`: `const registerCommand = pickFunction(asRecord(ctx), ['registerCommand','command','addCommand']); if (registerCommand !== undefined) { … registeredCommands.push(EVO_COMMAND_NAME); … }`.
  - Both blocks unconditionally `registeredCommands.push(EVO_COMMAND_NAME)`; there is no dedup against the first registration (the only guard, `else if (registeredCommands.length === 0)` at 3314, covers a diagnostics message, not registration).
- Analysis: on a host that exposes both `ctx.commands.register` and any of `ctx.registerCommand|command|addCommand`, `/evo` is mounted twice with two different handlers (one via `handleDshCommand`→`runFromCommand`, one directly), producing duplicate executions/output per invocation and a doubled `registeredCommands` entry. All e2e fixtures provide only one of the two shapes, so the collision is untested. The comment's "takes precedence" is not implemented.
- Fix: gate the fallback with `else if (dshRegister === undefined && registerCommand !== undefined)`, or skip it when `registeredCommands.includes(EVO_COMMAND_NAME)`.

### [INT-5] `logging.level` / `logging.includeTrajectorySummaries` are dead config (P2)
- File: src/config.ts:101-105, 462-465, 552, 1138-1149 (declared, defaulted, validated); consumers: none
- Evidence: `grep -rn "logging\.\|includeTrajectorySummaries\|logging\.level" src --include="*.ts"` outside config.ts returns only the doc comment at src/index.ts:244. The plugin's `log()` (src/index.ts:2552-2561) hardcodes levels `'info' | 'warn'` and ignores `config.logging.level`; no module reads `includeTrajectorySummaries`. README's configuration reference documents both leaves as live defaults (78-leaf table).
- Analysis: a host setting `logging.level: 'silent'` (or `includeTrajectorySummaries: true`) gets no behavior change; the validator accepts and freezes a no-op key. Dead config surface contradicts the repo's own "every key is one the plugin reads" claim (README:113).
- Fix: either honor them (route `log()` through `config.logging.level`; have the reflector/composer gate trajectory summaries on `includeTrajectorySummaries`) or remove the group from the schema, defaults, validator and README table in one change.

### [INT-6] Reward-contract identity literals copied by hand at two seams (P2)
- File: src/dsh-bridge/real-benefit-controller.ts:1772-1773; src/orchestrator.ts:2885 and src/orchestrator.ts:647-665 (`metadata['jit']`); counterparts src/jitrl/reward-contract.ts:56,65,591 and src/jitrl/jit-active-policy.ts:82
- Evidence:
  - real-benefit-controller.ts:1772-1773 hardcodes `contractVersion: 'r4/verifier-first-v1', aggregation: 'trajectory-signals-v1'` — even though line 122 of the same file already imports from `'../jitrl/reward-contract'`; `REWARD_CONTRACT.version`/`REWARD_CONTRACT.aggregation` are the single source (reward-contract.ts:90-111).
  - orchestrator.ts:2885 hardcodes `verifierFirstRule: 'verifier-first-completion-v1'` while reward-contract.ts:591 exports `REWARD_CONTRACT_VERIFIER_FIRST = 'verifier-first-completion-v1'` with zero importers (`grep -rn REWARD_CONTRACT_VERIFIER_FIRST src` → only the definition).
  - orchestrator.ts:647-651 `readJitBatchDiagnostics` reads `metadata['jit']` as a local literal while jit-active-policy.ts:82 exports `JIT_BATCH_METADATA_KEY = 'jit'` (the comment at 443-447 says the duplication is deliberate to avoid importing src/jitrl/**; the risk is a rename on one side only).
- Analysis: two modules must agree on these strings; the producer side bumps `REWARD_CONTRACT_VERSION` to r5 and the real-benefit controller keeps stamping r4 — a silent version fork across the real-benefit evidence chain. The orchestrator cases are mitigated by comments but are exactly the "each module hardcodes its own copy" pattern the shared-constants module exists to prevent.
- Fix: in real-benefit-controller.ts replace the literals with `REWARD_CONTRACT.version`/`REWARD_CONTRACT.aggregation`; in orchestrator.ts use `REWARD_CONTRACT_VERIFIER_FIRST`; for the metadata key, either accept the documented duplication but add a compile-time witness test asserting `JIT_BATCH_METADATA_KEY === 'jit'` is the string `readJitBatchDiagnostics` reads, or move the constant into `src/types/contracts.ts` (which orchestrator already imports).

### [INT-7] `handleFallbackEvent` runs are invisible to `settle()` and `dispose()` (P2)
- File: src/index.ts:3165-3199 (`handleFallbackEvent` returns `runFallback(...)` directly) vs src/index.ts:3200-3201 (`handleTriggerFailure`/`handleTurnCompleted` use `trackRun(...)`)
- Evidence:
  - src/index.ts:3200-3201: `handleTriggerFailure: (failure) => trackRun(runFallback(failure)), handleTurnCompleted: (turn) => trackRun(runCompletedTurn(turn)),`
  - src/index.ts:3187-3198: `handleFallbackEvent` ends with `return runFallback({…})` — no `trackRun`.
  - `settle()` (3202-3216) drains `triggeredRuns` only; `dispose()` (3233-3270) awaits `triggeredRuns` before `orchestrator.dispose()`.
- Analysis: `handleFallbackEvent` is the documented fallback entrypoint for hosts without an event subscriber (README:176-178), yet its in-flight runs are not joined: `settle()` returns early and `dispose()` proceeds to `runtimeControl.dispose()` + `orchestrator.dispose()` while such a run may still be mid-`executeRun`, aborting probes mid-flight on teardown. Same bug shape the `settle()` docstring says it exists to prevent.
- Fix: `handleFallbackEvent: (payload) => trackRun(runFallbackNormalized(payload))` — i.e. wrap the normalized fallback in `trackRun` like the other two entries.

### [INT-8] Online-experience dedup keys are consumed before the store append commits (P3)
- File: src/orchestrator.ts:2800-2812 (marking) vs src/orchestrator.ts:2960-2965 (append in try/catch)
- Evidence: the dedup loop adds every record key to `this.appendedExperienceKeys` **before** `await kernel.store.append(deduped)`; the catch handler pushes `'record_experience failed: …'` and returns 0 without releasing the keys, so a re-entered recorder can never re-append a batch whose append failed (the guard at 2803 `continue`s them as "already appended").
- Analysis: the pre-commit marking exists for re-entrancy protection, but it also permanently suppresses retry after a transient store failure within the same process. Quality-record rollback around the append (2938-2971) is correctly symmetric; only the dedup ledger is not.
- Fix: collect `marked` keys in a local list and delete them from `appendedExperienceKeys` in the append catch path (mirror of the `pendingQualityRegistrations` rollback).

### [INT-9] `EvoHarnessOrchestratorImpl.unregisteredQualityRecords` is write-only (P3)
- File: src/orchestrator.ts:992 (field), src/orchestrator.ts:2957 (sole writer); no reader
- Evidence: `grep -n unregisteredQualityRecords src/orchestrator.ts` → 992, 2957 only. Every pre-commit rollback pushes the record into the array; nothing ever reads, bounds or clears it.
- Analysis: dead store that grows once per rolled-back task-quality record for the process lifetime (retains full `ExperienceRecord` objects), and a misleading name — the actual rollback is performed by `unregisterAuthenticatedQualityRecord` + the `pendingQualityRegistrations` re-register on success.
- Fix: delete the field, or keep a bounded count if a future consumer needs the rollback audit trail.

### [INT-10] Unused fallback indirection `forwardingBranch` fallback arg desync (P3)
- File: src/index.ts:2202 vs src/index.ts:2356-2358
- Evidence: `runBranch: options.deps?.runBranch ?? options.runBranch ?? agentExecutor?.runBranch ?? unconfiguredBranchExecutor(now)` — the loud-failure executor is inlined at the deps level while `forwardingBranch(holder, fallback)` was designed to receive exactly that fallback; since the helpers are unwired (INT-1), any future re-wiring must remember to pass the same four-level chain or the two defaults can diverge (e.g. `agentExecutor?.runBranch` forgotten in the forwarder).
- Analysis: duplicate default resolution logic in two places for the same seam; only one place is live today. Fixing INT-1 must collapse this to a single chain, otherwise the fix itself introduces a second source of truth.
- Fix: resolve the branch chain once (`const resolvedRunBranch = options.deps?.runBranch ?? options.runBranch ?? agentExecutor?.runBranch ?? unconfiguredBranchExecutor(now)`) and hand it both to `deps` and (after INT-1) to `forwardingBranch` as the pre-set default.

## Positive verifications

### [PV-1] Every production model call is wrapped in metering; no direct `complete()` bypass
All seven stages wrap their adapter at construction: proposer `createMeteredModelAdapter(options.model, 'propose', …)` (src/harness2/proposer.ts:758), composer `'compose'` (composer.ts:571), reflector `'reflect'` (reflector.ts:572), offline dreamer `'dream'` (offline-dreamer.ts:1871), step evaluator `'evaluate_steps'` (step-evaluator.ts:983), logit probe `'logit_probe'` (logit-sources.ts:209), same-process probe branch `'probe'` (branch.ts:250). `grep -rn "\.complete(" src` finds no direct inner call outside `metered-model-adapter.ts` (the only hit is the dead INT-1 helper). `createLlmModelAdapter` stamps `metadata.rawUsage` + `countingSemantics` (src/dsh-bridge/model.ts:589-590,617-618), which the metered adapter consumes for ledger settlement (metered-model-adapter.ts:590-592) — the metering chain is coherent end-to-end.

### [PV-2] JitRL runtime switch: one control, complete surface vocabulary, single write path
`JIT_SURFACES` (src/jitrl/runtime-control.ts:38-46) covers every surface name read across modules (`meta` via the L1 `isRuntimeEnabled` lockstep object, `proposal`/`onlineRecord` in src/orchestrator.ts:2313/3111, `hostRecord`/`advisor`/`mirror`/`dreamJit` in src/index.ts:2591-2604/2753/2179); `isEnabled` fails closed on an unknown surface (runtime-control.ts:114-118); `/evo jit off` writes once through `jitCommandController.setEnabled` (src/index.ts:2835-2844) updating both the control and the decorator's legacy object, so no second source of truth exists. Orchestrator re-reads generation around external effects (src/orchestrator.ts:2347,2367-2375, 3150,3160-3176), so a mid-flight switch cannot publish results.

### [PV-3] Trigger wiring matches the verified DSH catalog; disposers are owned and torn down
Default subscriptions are exactly `session/event`/`agent/error`/`agent/status` (src/host-triggers.ts:46-60), with the fabricated `task:failed`/`tool:error` only reachable behind explicit `autoFallbackEvents` opt-in (host-triggers.ts:801-812, index.ts:3406-3410). Every listener's disposer is collected (index.ts:3396-3398) and disposed before `runtimeControl.dispose()`/`orchestrator.dispose()` in `plugin.dispose()` (3247-3269), and `agent.runMaintenance` races are contained (host-triggers.ts:740-747). Payload classification is shared by all transports through the same `classifySessionEvent`/`classifyAgentError` functions — no second normalization copy exists.

### [PV-4] Version identity is single-sourced on the main learning path, and the persistence counter contract holds
`recordOnlineExperience` stamps `rewardVersion: REWARD_CONTRACT.version`, `provenanceVersion: CURRENT_PROVENANCE_VERSION`, `experienceSchemaVersion: EXPERIENCE_SCHEMA_VERSION` from imports (src/orchestrator.ts:125, 2696-2698), and the store facade re-stamps unversioned producers with the same constants (src/jitrl/index.ts:276-287), so consumers (`isRewardVersionExact` at experience-store.ts:1436,1464; write-back gate at orchestrator.ts:2199-2205) cannot fork from the producers. `PolicyStore` structurally satisfies `OrchestratorTaskCounter` (`shouldDream`/`recordCompletedTask`/`recordDream`, src/persistence/policy.store.ts:372-404) and is wired as `deps.taskCounter` (src/index.ts:2216-2218). No import cycle exists into `src/index.ts` or `src/orchestrator.ts` (only index imports orchestrator), and the orchestrator keeps its jitrl decoupling via the injected `OrchestratorJitRl` structural surface.

### [PV-5] The eight surfaces are reachable through the hook adapter and observable per-surface
`SURFACE_HOST_METHOD` maps all `HARNESS_COMPONENT_KEYS` (src/cordis-seams/eight-surfaces.ts:55-64); `DshHookHostAdapter` implements `registerPromptSegment`/`registerGuardrails`/`mountMiddleware` natively and forwards `forkBranch`/`registerMemoryScope`/`patchToolGuidance`/`mountSkills`/`mountScripts`/`registerSubagents`/`acquireSandbox` to the structural fallback adapter (src/cordis-seams/dsh-hook-host-adapter.ts:1885-2018), so with the documented fallback (src/index.ts:1166-1183) all ten adapter methods exist. Mount attempts are recorded per surface (`recordSurfaceMount`, dsh-hook-host-adapter.ts:910-933), surfaced via `stats().surfaceMounts`, and consumed by `surfaceStatusSnapshot` (src/index.ts:1012-1039) — enabled/mountable/lastMountResult stay honest (collect-or-omit).
